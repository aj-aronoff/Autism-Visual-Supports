01

The shape of the agent

Every request goes to the router, a single gpt-4o-mini call with three function schemas attached. The router decides which tool to run, the tool runs locally, its output is appended to the message list, and control returns to the router. That loop repeats until the router answers in plain text instead of asking for a tool.

Nothing in the loop is a planner. The entire plan is whatever the model happens to emit as a tool call on each turn, which is exactly why the course spends its later lessons measuring the path the agent took rather than only its final answer.

02

The three tools

Each tool is a block of multi-step logic, not a single API call. The step counts matter: they are the spans the tracing lesson will ask you to instrument, and the places a failure can hide.

Database lookup

lookup_sales_data(prompt)

  1. 1Read the parquet file into a DuckDB table named sales
  2. 2Ask the model to write SQL, given the column names and the user’s unchanged prompt
  3. 3Strip markdown fences, execute, return df.to_string()

1 model call · text‑to‑SQL

Data analysis

analyze_sales_data(prompt, data)

  1. 1Interpolate the rows and the question into one prompt and return the model’s prose

The simplest tool and the hardest to grade. There is no ground truth for “what trends do you see”, so this is where LLM‑as‑a‑judge earns its place.

1 model call · open‑ended output

Data visualization

generate_visualization(data, goal)

  1. 1Produce a chart config (type, x, y, title) as a structured Pydantic object
  2. 2Turn that config into Python plotting code

Split in two because one call asked to pick a chart and write correct matplotlib does neither reliably.

2 model calls · sequential

One question, seven model calls

This is the trajectory from the actual lab run, for the query “Show me the code for graph of sales by store in Nov 2021, and tell me what trends you see.” The notebook printed three router calls and two rounds of tool execution, so the second round dispatched two tools at once.

  1. 1
    router → lookup_sales_data
    The router reads the question and asks for data first.
  2. 2
    generate_sql_query
    Writes SELECT over the sales table; DuckDB executes it; 33 rows come back as one string.
  3. 3
    router → generate_visualization + analyze_sales_data
    Two tool calls in a single turn, both handed the lookup output.
  4. 4
    extract_chart_config
    Structured output call. This is the one that silently failed.
  5. 5

  6. 6

    Produces the “Trends Observed” prose.
  7. 7
    router → final answer
    No tool calls. The router composes code and commentary into one reply.
04

The bar chart that wasn’t

The lab asks tool 3 for “A bar chart of sales by product SKU. Put the product SKU on the x-axis and the sales on the y-axis.” It returned plt.plot() and rendered a line.

What the lab produced
What was asked for

Both panels plot the same 30 rows: store 1320, 1 November 2021, sales value per SKU. The left panel places SKUs at their numeric positions, which is why it bunches and why the real notebook’s x‑axis reads 6.175…6.195 with a 1e6 offset.

Three fingerprints of the fallback path

  • 1chart_type came out "line", which is the hardcoded value in the except branch.
  • 2The chart title is the entire request sentence, verbatim. The fallback sets "title": visualization_goal. A real config would have said “Sales by Product SKU”.
  • 3SKU codes were plotted on a continuous axis, so the x‑axis carried a 1e6 offset label instead of category ticks.

The cause is one attribute access. A structured-output response puts the parsed model on .parsed; .content is still the raw JSON string, so content.chart_type raises AttributeError and the bare except swallows it.

# notebook
content = response.choices[0].message.content   # a str
return {"chart_type": content.chart_type, ...}       # AttributeError → fallback

# fixed
parsed = response.choices[0].message.parsed    # a VisualizationConfig
return {"chart_type": parsed.chart_type, ..., "used_fallback": False}

Two consequences worth sitting with. First, every chart the lab produces is a line chart no matter what you ask for, and nothing in the output says so. Second, the fallback config names columns date and value that do not exist in this dataset, yet the generated code labelled the axes “Product SKU” and “Total Sales Value” correctly. The code-writing model ignored the broken config and re-derived everything from the data blob, which means step 1 of tool 3 contributed nothing at all to the output.

This is the course’s own argument in miniature. The run did not crash, nothing was logged, the answer looked plausible, and the only way to catch it is an evaluator that checks the chart type against the request.

06

Seven defects in the lab code

None of these stop the notebook from running. That is the point. Each one is a place where the agent can be wrong while looking fine.

#Lab codeProblemFix
1message.content Structured output read off the wrong attribute, so every chart silently falls back to a line message.parsed
2parse() outside try Only the attribute access is protected, so a real API error kills the tool instead of falling back Wrap the call
3while True: A router that keeps requesting tools never exits Cap the turns
4CREATE TABLE IF NOT EXISTS A changed parquet file is ignored for the rest of the session CREATE OR REPLACE
5return f"Error: {e}" A failure is returned as an ordinary string, so the router cannot tell it apart from data Tag it TOOL_ERROR:
6exec(code) Model-written Python executed unread, in the same process Return the string
7to_string() Rows pass between tools as formatted text, so the dataset is re-sent and re-parsed by the model Pass a handle

Defect 7 is visible in the final answer of the real run: the model copied the entire lookup result back out as a hardcoded data = [...] literal inside the chart code it wrote.

What there is to evaluate

Every component gets its own evaluator, and the path through them gets one more. The label on each item is the kind of evaluator that fits it.

Router R

  • truthPicks the right tool for the question
  • truthFills parameters from the user’s actual words
  • truthAnswers directly when no tool is needed
  • codeTerminates within the turn cap
  • codePasses tool 1’s real output to tools 2 and 3

Lookup T1

  • codeGenerated SQL parses and executes
  • truthResult matches a hand-written query
  • codeMarkdown fences stripped
  • codeRead-only; no DDL or DML slips through
  • codeFailures surface as errors, not as data

Analysis T2

  • judgeAnswers the question that was asked
  • judgeEvery figure cited appears in the input rows
  • judgeNo invented trend beyond the data’s range
  • humanUseful to a store owner

Visualization T3

  • truthChart type matches the request
  • codeFallback config never passes silently
  • codeAxes name real columns
  • codeGenerated code parses
  • judgeChart form suits the data

Trajectory X

  • truthTool sequence matches the expected path
  • codeNo repeated identical call
  • codeConverges in the expected number of turns
  • codeNo tool runs on an upstream error

System S

  • codeLatency and token cost per run
  • codeEvery span recorded, including failures
  • truthFixed dataset replays without regression
  • humanProduction traces annotated and fed back
