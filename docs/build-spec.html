Autism Visual Supports

An app that turns two minutes of what a parent already knows about their child into a printable, tappable visual support — and then tracks the one thing that decides whether the child keeps trusting it.

A.J. Aronoff · Build for the Future Hackathon 2026 · Theme: Building Apps that make a difference · Cash prize is paid to the nonprofit partner

The finding that shapes the build

Three prompts, one output contract

The three prompt drafts in this project look like alternatives. They aren't. Each one ends in the same three-part deliverable, which means the app has a single, stable output shape rather than one per tool type.

Prompt draftShapeWhat it contributes to the build
visual-support-promptFill-in template, single shotThe API contract — every field the generator needs, named
prompt-gem-stylePersona + 3-question intakeThe system prompt and the image-prompt style rules
if-then-board-prompt5-step interactive coachThe intake wizard and special-interest theming

All three resolve to: cards → caregiver script → implementation guidance. That triple is the data model. Everything below follows from it.

Take 5
Break

Delivered before the event, not during it.

Glyphs stand in for the generated artwork. In the app each card carries a real photo, a flat icon, or line art, per the child's recorded visual preference — the same card image is reused everywhere that activity appears, because changing the picture breaks the predictability the support exists to provide.

The differentiator

The app tracks reward delivery, not board creation

“Otherwise, your child may not trust the board the next time you use it.”

The toolkit states the failure mode plainly: a First–Then board works only if the “then” is actually delivered the moment the “first” task is done. A generator that stops at a pretty PDF has solved the easy half. So every board in this app carries a usage log with one required field — RewardDelivered — and the home screen surfaces a trust streak per board rather than a count of boards made.

Vanderbilt Kennedy Center TRIAD / Autism Speaks ATN, Visual Supports and Autism (2011), First–Then Board

This is also what makes the app defensible against “just prompt a chatbot.” The chatbot produces the artifact. The app owns the loop: the child profile persists, cards are reused across boards, the log records what prompt level was needed, and the plan steps down the prompt hierarchy as independence grows.

Data model

Entities

Nine entities plus static entities. The profile is separate from the board so a parent fills in the hard part once, and every later board is three questions.

Child

Filled once. Owned by the parent.

  • Nickname text
  • AgeYears int
  • DevelopmentalStage → static
  • VisualStyle → RealPhotos | Icons | LineArt | WordsOnly
  • LanguageLevel → PreVerbal | EarlyReader | Reader
  • SpecialInterests text — drives theming
  • SensoryNotes, TriggerNotes text

Board

One generated support.

  • ChildId, SupportTypeId
  • Title, Goal, Obstacle
  • Environment → Home | Classroom | Community
  • Theme text
  • Status → Draft | InUse | Retired
  • AgentRunId — traceability
  • Version int

Card

The atomic unit. Ordered.

  • BoardId, SequenceNo
  • Role → First | Then | Step | Choice | Wait | Stop | Oops
  • Label text — max 3 words, validated
  • ImagePrompt text
  • Image binary
  • ImageSource → Generated | Uploaded | SymbolSet
  • AltText text

CaregiverScript

1–2 low-demand phrases per phase.

  • BoardId
  • Phase → Before | During | OnCompletion | IfRefusal
  • PhraseText text
  • WordCount int — fewest words wins

ImplementationPlan

One per board.

  • Placement text — fridge, binder, tablet
  • Reinforcement text
  • IfChallengingBehavior text
  • Generalization text

PromptStep

Ordered hierarchy, least intrusive first.

  • PlanId, Level int
  • Kind → VisualPoint | Gesture | Verbal | Model | PhysicalGuide
  • Instruction text

UsageLog

The loop. Logged from the tablet view in one tap.

  • BoardId, UsedOn datetime
  • Outcome → Independent | WithPrompt | Refused | Skipped
  • PromptLevelUsed int
  • RewardDelivered bool — required
  • Notes text

CardLibrary

Reuse beats regeneration.

  • ChildId, Label, Image
  • TimesUsed int
  • Looked up before any new image is generated

EvidencePractice

Static. The 11 National Standards practices.

  • Name, Description, Citation
  • Every board cites which it rests on
Screens

Flow

01

My Children

Child cards with each one's boards-in-use and trust streak. Not an empty dashboard — a parent with one child sees one card and their three live boards.

02

Child Profile

The one-time intake: age, visual style, language level, special interests, sensory and trigger notes. Everything the three prompt drafts ask in Step 1.

03

New Support — 3 questions

Which tool · what routine and what's hard about it · what motivator works. Tool choice can be suggested from the obstacle text rather than asked.

04

Board Editor

Reorder cards, edit labels against the three-word validator, regenerate one card's image, or swap in a photo from the child's own life. Photos of the real bathroom beat stock art.

05

Script & Plan

The caregiver phrases and the prompt hierarchy, on their own tab, because this is the part that gets skipped and shouldn't be.

06

Use it — two outputs

Print sheet: card grid with cut lines, sized for lamination and Velcro. Tablet mode: full screen, large targets, tap to check off, works offline.

07

Log, by text message

Twilio sends the caregiver script when the routine is due and asks one question afterwards: did the reward happen? The reply writes the log. In-app logging stays for anyone who wants to add prompt level and notes.

08

Share with the team

Read-only board access for a teacher, aide, or SLP. The toolkit's point about using the same visuals across settings is the whole reason this exists.

AI & integrations

Three agents, grounded and fenced

“Particularly Agentic AI” is in the rules, so generation is an orchestrated workflow in ODC's Agent Workbench rather than a single prompt. Three agents, each with a job small enough to judge, and a reasoning path the jury can watch inside the demo.

  • Composer reads the child profile and the obstacle, chooses the support type, and drafts cards, script, and plan against its knowledge source — the Vanderbilt TRIAD toolkit and the National Autism Center's 11 practices. It names the practice each board rests on.
  • Reviewer checks that draft against the design rules and sends it back: three-word labels, positive phrasing, a Then card present, card count in range. A second agent catching the first one's drift is the most legible AI moment available in five minutes.
  • Illustrator searches the child's existing card library before it generates anything, so a given activity keeps the same picture forever. Predictability is the product.
  • Tools: GetChildProfile · SearchCardLibrary · CreateBoard · AddCard · SetScript · SetPlan · GenerateCardImage · SendRoutineSms. Models come from the Azure OpenAI and Amazon Bedrock tokens bundled into the ODC instance.
  • Twilio closes the loop. A parent at the front door is holding shoes, not a tablet. So the caregiver script arrives by SMS when the routine is due — “First shoes, then swing.” — and one question follows it: “Did the swing happen? Reply Y or N.” That reply writes UsageLog.RewardDelivered. The single field this product turns on is the one nobody would ever open an app to fill in.
  • Traceability: Agent Workbench exposes each agent's reasoning and tool calls, and Board.AgentRunId pins every board to the run that made it.

Guardrails

Enforced in the app, not asked for in the prompt

Each of these is a validation in a server action, so a model that drifts cannot ship a bad board.

01

Three words maximum per label. Reject and re-ask. The toolkit's limit, not a style preference.

02

Positive phrasing only. “Don't run” is rejected in favour of “Walk.” A blocklist of negation forms catches it.

03

A First–Then board cannot save without a Then card. The reward is structural, not optional.

04

Card count within the type's range. A 12-step morning schedule for a pre-verbal four-year-old is a failure, not thoroughness.

05

No diagnosis, no clinical advice. When the obstacle text describes self-injury, aggression, or escalation, the app says so and surfaces referral guidance instead of generating a board.

06

Neurodiversity-affirming language, checked. Supports, not compliance; “autistic child” unless the parent's profile says otherwise.

07

Parent owns and can export everything. Child profiles are the most sensitive data in the app and are never training input.

Open

Decisions still to make

  • Solo, or recruit before 28 October? One to five members are allowed and solo is permitted, but UX/UI is a full quarter of the score and the window is seven days. A designer and a second ODC developer would lift three of the four criteria at once. After 28 October the team is fixed.
  • Scoring weights arrive at kickoff. The rules say detailed criteria come on 2 November. Day one of the build is partly a re-planning day, so hold the roadmap items loosely.
  • Card artwork source. Generated icons are fast and free-form; an established symbol set is more predictable and more familiar to children already using PECS. A parent's own photos beat both. The model supports all three — which is the demo default?
  • Autism Speaks, or a local partner? Both the rules and the FAQ push toward a nonprofit the team already has a relationship with — one that can advise during the build and would genuinely use a 12-month ODC license. A local chapter, an autism school, or a school district's SLP team beats a national logo on both counts, and gives the demo one real test family. The organizers will make introductions if asked.
  • Offline depth. Full offline board use is the right product answer and a real build cost. Read-only cached boards may be enough for the demo.
